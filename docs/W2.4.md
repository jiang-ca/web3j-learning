# W2.4｜查询交易

状态：🔄 进行中

# 一、本节目标

根据 Transaction Hash 调用：

```text
eth_getTransactionByHash
```

取得完整交易对象，并理解：

```text
hash
blockNumber
blockHash
transactionIndex
from
to
nonce
value
gas
gasPrice
input
type
```

本节示例会自动从最近区块找到一笔交易 Hash，所以不需要手动去区块浏览器复制交易。

# 二、完整示例

源码：

```text
src/main/java/com/example/web3jstudy/w2/TransactionQueryDemo.java
```

本节代码先使用已经掌握的区块查询找到一笔近期交易，再执行：

```java
EthTransaction response =
        web3j.ethGetTransactionByHash(
                transactionHash)
                .send();
```

然后：

```java
Transaction transaction =
        response.getTransaction()
                .orElseThrow(...);
```

取得完整交易对象。

完整源码以仓库中的 `TransactionQueryDemo.java` 为准。

# 三、eth_getTransactionByHash

该 RPC 只需要一个参数：

```text
Transaction Hash
```

返回：

```text
Transaction Object
```

如果查不到，则 `result = null`。

Web3j 使用：

```java
EthTransaction
```

承载 JSON-RPC Response。

真正的交易对象是：

```java
Transaction
```

关系：

```text
eth_getTransactionByHash
↓
EthTransaction
↓
result
↓
Transaction
```

# 四、Transaction Hash

```java
transaction.getHash()
```

交易 Hash 是交易的主要标识。

后面的：

```text
查交易
查 Receipt
查 Logs
对账
排查异常交易
```

都会经常使用 Transaction Hash。

不要与：

```text
Block Hash
```

混淆。

# 五、交易属于哪个区块

已经被区块收录的交易通常可以读取：

```java
transaction.getBlockNumber();
transaction.getBlockHash();
transaction.getTransactionIndex();
```

分别代表：

```text
blockNumber
→ 所属区块高度

blockHash
→ 所属区块 Hash

transactionIndex
→ 这笔交易在该区块 transactions 数组中的位置
```

如果交易仍然 pending，这些字段可能还没有确定。

本节自动选择的是已经存在于区块中的交易，因此这些字段应当有值。

# 六、From 与 To

```java
transaction.getFrom();
transaction.getTo();
```

`from`：

```text
交易发送方地址
```

`to`：

通常是：

```text
交易接收地址
或
被调用的合约地址
```

但如果这是一笔合约创建交易：

```text
to = null
```

因此代码不能假设所有交易一定有 `to`。

# 七、Nonce

```java
transaction.getNonce()
```

Nonce 是发送方账户用于交易顺序管理的序号。

例如同一个地址连续发送：

```text
Nonce 10
Nonce 11
Nonce 12
```

它与：

```text
transactionIndex
```

不是同一个概念。

```text
Nonce
→ 同一个发送账户的交易序号

transactionIndex
→ 交易在某个区块里的位置
```

Nonce 的发送与并发问题会在 W5.3 专门展开。

# 八、Value

```java
transaction.getValue()
```

得到：

```java
BigInteger
```

单位为：

```text
Wei
```

再转换：

```java
BigDecimal valueBnb =
        Convert.fromWei(
                new BigDecimal(valueWei),
                Convert.Unit.ETHER);
```

得到交易本身携带的原生 BNB 数量。

这里有一个非常重要的边界：

```text
transaction.value
≠
BEP-20 Token 转账数量
```

例如一笔 USDT Transfer：

```text
transaction.value
可能是 0 BNB

但合约内部
可能转了 100 USDT
```

Token 数量需要从合约调用 / Event Log 中解释，后面 W3、W4 学习。

# 九、Gas 与 Gas Price

交易对象中的：

```java
transaction.getGas()
```

代表：

```text
这笔交易提供的 Gas Limit
```

不是：

```text
最终实际消耗的 Gas
```

实际：

```text
gasUsed
```

要从 Transaction Receipt 查询。

这正是下一节 W2.5 的内容。

`gasPrice` 是交易对象提供的 Gas Price 字段，单位为 Wei。

示例中同时转成 Gwei：

```java
Convert.fromWei(
        new BigDecimal(gasPriceWei),
        Convert.Unit.GWEI)
```

方便阅读。

完整手续费不能简单用交易对象里的字段直接下结论；实际执行的 Gas、状态和 Receipt 相关字段下一节再处理。

# 十、Input

```java
transaction.getInput()
```

是交易携带的数据。

简单原生 BNB 转账经常看到：

```text
0x
```

而合约调用通常会携带 calldata：

```text
0x + 函数选择器 + ABI 编码参数
```

合约创建交易的 input 中还可能包含部署字节码和构造参数。

现在不要求解码 input。

到了 W3 学 ABI 后，才能真正解释：

```text
这串 input 到底调用了哪个函数
传了哪些参数
```

# 十一、Transaction 与 Receipt 的区别

这是 W2.4 最重要的概念之一。

Transaction 更接近：

```text
这笔交易提交了什么？
```

它告诉你：

```text
谁发的
发给谁
带多少 BNB
Nonce 是多少
Gas Limit 是多少
Input 是什么
```

但是只拿到 Transaction 还不能完整回答：

```text
交易最终执行成功了吗？
实际用了多少 Gas？
产生了哪些 Event Logs？
```

这些属于：

```text
Transaction Receipt
```

所以：

```text
Transaction
→ 请求 / 交易内容

Receipt
→ 执行结果
```

下一节 W2.5 会直接用本节的 Transaction Hash 查询 Receipt。

# 十二、为什么示例自动查找最近交易

上一节实际碰到过：

```text
交易数量：0
```

所以如果始终只查询：

```text
LATEST
```

不能保证那个区块一定有交易。

本节示例会：

```text
latest
↓
如果没有交易
↓
latest - 1
↓
latest - 2
↓
...
```

最多向前找 20 个区块。

一旦找到：

```text
Transaction Hash
```

再执行本节真正的：

```text
eth_getTransactionByHash
```

这只是为了让示例可以独立运行，不改变本节核心知识点。
